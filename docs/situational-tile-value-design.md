## 0. ข้อค้นพบหลัก (อ่านแค่นี้ก็พอ)

**เอนจินคำนวณ "แผนที่ความเป็นไปได้" ของทั้งกระดานอยู่แล้วทุกตา แล้วโยนทิ้ง**

`Generator::computeCross()` ([movegen.cpp:147](../src/movegen.cpp)) สร้างสิ่งนี้ให้ทุกช่องว่างบนกระดาน:

- `mask` — บิต 26 ตัว บอกว่า **token ไหนบ้างที่ลงช่องนี้แล้วสมการแนวตั้งฉากยังถูก**
- `fixedSum` — แต้มของเบี้ยเดิมในสมการนั้น
- `has` — ช่องนี้สร้างสมการไขว้หรือไม่

และ `IncrementalBoard` ([inc_board.hpp](../src/inc_board.hpp)) ก็ maintain `crossV`/`crossH`
ไว้ข้ามการ make/unmake อยู่แล้ว **ข้อมูลชุดนี้คือคำตอบตรง ๆ ของทุกอย่างที่ต้องการ**
— "ช่องไหนต้องใช้ `=` เท่านั้น", "ช่องไหนต้องใช้ 5 เท่านั้น", "ทั้งกระดานมี `=` เปิดไหม" —
แต่มันถูกใช้เพื่อ **prune DFS อย่างเดียว** ไม่มีบิตไหนไปถึง `eval.cpp` เลย

สิ่งที่ไปถึงฝั่งประเมินค่าคือ `BoardContext` ซึ่งมี 5 ตัวเลข และ

| ฟิลด์ | สถานะจริงในโค้ดวันนี้ |
|---|---|
| `mobility` | นับช่องว่างที่ติดเบี้ย หาร 40 → **ตัวเลขเดียวที่บอกรูปกระดาน** |
| `freshTileValue` | ค่าเฉลี่ยของกอง ใช้ตอนแลกเบี้ย |
| `scoreDiff` | ใช้ใน λ และโบนัสแลกเบี้ย |
| `bagSize` | **เขียนแล้วไม่เคยถูกอ่าน** (`grep` ยืนยัน: เจอที่ eval.cpp:13 ที่เดียว) |
| `unseenTotal` | **เขียนแล้วไม่เคยถูกอ่าน** |

ผลคือ `leaveValue()` ตัดสินว่าควรเก็บ `=` ไว้ไหม จากตัวเลข "จำนวนช่องว่างที่ติดเบี้ย"
มันจึงแยกไม่ออกระหว่าง

- กระดานที่มี 40 ช่องว่าง และ **ทุกช่องต้องใช้ `=` เท่านั้น** (→ `=` มีค่ามหาศาล)
- กระดานที่มี 40 ช่องว่าง และ **ไม่มีช่องไหนต้องใช้ `=` เลย** (→ `=` เกือบไร้ค่า)

สองกระดานนี้ตรงข้ามกันโดยสิ้นเชิง แต่เอนจินให้ตัวเลขเดียวกัน
และเพราะ `leaveValue` คือทั้ง (ก) ตัวจัดอันดับ candidate ก่อนเข้า sim
(ข) นโยบายของคู่ต่อสู้ที่จำลอง ([opponent_search.cpp:123](../src/opponent_search.cpp))
(ค) endpoint evaluator ของ endgame ([opponent_search.cpp:75](../src/opponent_search.cpp))
— ความผิดพลาดนี้จึงถูกคูณเข้าไปในทุกชั้นของการคิด

**แผนนี้คือ: ทำให้ข้อมูลที่มีอยู่แล้วเดินทางไปถึงฟังก์ชันค่า แล้วให้ค่าเบี้ยเป็นฟังก์ชันของมัน**

## 1. โมดูลใหม่: `src/space_map.hpp` / `space_map.cpp`

### 1.1 นิยามพื้นที่ 2 ประเภท ตามที่ต้องการ

**พื้นที่ไขว้ (HookSite)** — ช่องว่าง 1 ช่องที่ลงเบี้ยแล้วเกิดสมการตั้งฉาก
กติกา A-Math บังคับว่าทุก run ยาว ≥ 2 ต้องเป็นสมการที่สมบูรณ์ (มี `=`)
ดังนั้นถ้า run เดิมในแนวตั้งฉาก **ยังไม่มี `=`** เบี้ยที่เราลงต้องเป็น `=` เอง
→ `mask` ที่ movegen คำนวณไว้ **เข้ารหัสข้อเท็จจริงนี้อย่างแม่นยำอยู่แล้ว**
`mask == (1u << T_EQ)` คือช่องที่ "ต้องใช้ `=` เท่านั้น" ไม่ต้องเดา ไม่ต้อง heuristic

**พื้นที่ขยาย (ExtendSite)** — ช่องว่างต่อเนื่องที่ต่อท้าย/ต่อหน้าสมการเดิมในแนวเดียวกัน
เช่น `5×3=15` → `5×3=15÷1` หรือ `3+4=7` → `3+4=7=7`
จุดสำคัญคือ **`=` มาจากกระดาน ไม่ต้องจ่ายจากมือ** — นี่คือเหตุผลที่พื้นที่ขยาย
เป็นตัวหารของ "ค่าของ `=`" ตามที่คุณอธิบาย

```cpp
struct HookSite {
  uint16_t cell;
  uint8_t  dir;              // ทิศของ pass ที่ทำให้เกิด cross run
  uint32_t tokenMask;        // = movegen cross[].mask ตรง ๆ
  uint8_t  tokenCount;       // popcount(tokenMask)
  bool     requiresEquals;   // tokenMask == {T_EQ}
  bool     equalsOnBoard;    // run เดิมมี '=' อยู่แล้ว → เล่นได้โดยไม่ต้องมี '='
  int16_t  bestScore;        // max ของ crossScoreFor() ทุก token ที่ลงได้
  uint8_t  bestToken;
};

struct ExtendSite {
  uint16_t anchorCell;
  uint8_t  dir, length;      // ช่องว่างที่ใช้ได้ก่อนชนสิ่งกีดขวาง
  uint32_t kindMask;         // TileKind ที่ปรากฏใน extension ที่ถูกกฎอย่างน้อย 1 แบบ
  int16_t  bestScore1;       // แต้มดีที่สุดถ้าลง 1 เบี้ย
  int16_t  bestScore2;       // ถ้าลง 2 เบี้ย
};

struct SpaceMap {
  std::vector<HookSite>   hooks;
  std::vector<ExtendSite> extends;

  // ── ตัวรวมที่ฝั่งประเมินค่าอ่านจริง ──
  uint8_t  sitesForToken[ASSIGNED_COUNT];      // มีกี่ช่องที่รับ token นี้
  int16_t  bestScoreForToken[ASSIGNED_COUNT];  // แต้มดีที่สุดของ token นี้ทั้งกระดาน
  uint16_t equalsGatedSites;    // ช่องที่รับเฉพาะ '='
  uint16_t equalsFreeSites;     // ช่องที่เล่นได้โดยไม่ต้องมี '=' ในมือ
  uint16_t extendCapacity;      // Σ length ของ ExtendSite
  uint16_t heavyPlaceableSites; // ช่องที่รับ token 10..20 ได้
  uint16_t newEquationCapacity; // บริเวณว่างที่ยาวพอจะตั้งสมการใหม่ทั้งอัน
};
```

### 1.2 ต้นทุน

- `hooks` = **อ่านตรงจาก `crossV`/`crossH`** ถ้าเดินผ่าน `IncrementalBoard` ก็แทบฟรี
  ถ้าไม่ ก็คือ pass เดียวขนาด 225 × 26 `validateLine` — ซึ่ง movegen จ่ายอยู่แล้วทุกครั้ง
- `extends` = ค้นแบบ exhaustive ลึก 1–2 เบี้ยต่อ site ซึ่งถูกจำกัดด้วยเรขาคณิต
  และกติกา (เลข ≤ 3 หลัก, เลข 10–20 ห้ามติดกัน) → หลักร้อย `validateLine` ต่อตา

รวมแล้วต่ำกว่า 1 ms เทียบกับ budget 120 วินาที **นี่คือจุดขายของแผนนี้ทั้งหมด:
มันแทบไม่มีต้นทุนเพิ่ม เพราะเป็นการ "เก็บของที่คำนวณทิ้งอยู่แล้ว"**

### 1.3 การทดสอบที่ทำให้เชื่อถือได้ (สำคัญที่สุดในเอกสารนี้)

`tests/test_space_map.cpp` ต้องพิสูจน์ **invariant ความเท่ากันกับ movegen**:

> สำหรับทุกตำแหน่งในคลัง corpus และทุก `HookSite`
> token `t` อยู่ใน `tokenMask` **ก็ต่อเมื่อ** `generatePlaceMoves` ด้วยมือที่มีเบี้ยตัวนั้นตัวเดียว
> สร้างตาเดินที่ถูกกฎที่ช่องนั้นได้จริง — และแต้มที่ได้ต้องตรงกับ `bestScore`

นี่คือวินัยเดียวกับที่ใช้พิสูจน์ endgame solver เทียบ negamax (bag 0: 86/86)
ถ้าไม่มี invariant นี้ ฟังก์ชันค่าจะกำลังใช้เหตุผลกับกระดานที่ไม่มีอยู่จริง

## 2. ค่าเบี้ยแบบพลวัต

### 2.1 จุดเชื่อมต่อ: แก้บรรทัดเดียว

```cpp
struct BoardContext {
  // ... ของเดิม ...
  const SpaceMap* spaces = nullptr;
  float tileValue[KIND_COUNT];  // = base bias + การปรับตามสถานการณ์
  float equalsUrgency = 1.0f;
};
```

แล้วใน `leaveValue()` เปลี่ยน [eval.cpp:66](../src/eval.cpp)

```cpp
- v += g_leave.kindValue[k] * n;
+ v += ctx.tileValue[k] * n;
```

**แค่นี้ทั้งระบบก็ได้ตาใหม่** เพราะ `simulate`, `staticEquity`, `enumerateExchanges`,
`OpponentPolicyEvaluator` และ `EndpointEvaluator` ล้วนเรียกผ่าน `leaveValue`
คู่ต่อสู้ที่จำลองจะเริ่มหวง `=` ตามสถานการณ์เหมือนกัน → ฟังก์ชันค่าสมมาตรขึ้น
(ตรงกับข้อ 4.4 ของ [bot-strength-diagnosis](bot-strength-diagnosis.md))

### 2.2 สูตร

```
tileValue[k] = base[k] + gain(k) − glut(k)
```

**`gain(k) = demandPressure(k) × horizon`**

```
access(k)   = Σ over sites ที่ k ใช้ได้ ของ  bestScore(site,k) × exclusivity(site)
exclusivity = 1 / tokenCount(site)          // ช่องที่มีแค่เบี้ยเดียวลงได้ = ค่าสูงสุด
supply(k)   = myRack.n[k] + unseen.n[k]     // สำเนาที่ยังอยู่ในโลก
demandPressure(k) = access(k) / max(1, supply(k))
horizon     = clamp(1.2 − bagSize/60, 0.35, 1.2)   // ← bagSize ได้ถูกอ่านครั้งแรก
```

`horizon` คือคำตอบว่า "ช่องนี้จะยังอยู่ถึงตาหน้าของฉันไหม" —
ต้นเกมกระดานเปลี่ยนเร็ว ช่องสำคัญวันนี้พรุ่งนี้หาย จึงลดน้ำหนัก
ปลายเกมกระดานนิ่ง ช่องสำคัญคือของจริง จึงเพิ่มน้ำหนัก

**`glut(k)`** แทน `duplicatePenalty` แบบเหมารวม: ถือ n ตัวแต่กระดานมีที่ลงแค่ m ช่อง
→ ลงโทษเฉพาะส่วนที่เกิน `max(0, n − sitesForToken(k))` แบบ convex
("ถือ 19 สองตัวบนกระดานที่ไม่มีช่องรับเลขสองหลักเลย" จะถูกลงโทษหนักตามจริง
ซึ่งวันนี้ `heavyBurden` ผ่อนให้เมื่อ `mobility` สูง — ผิดทาง เพราะ mobility
ไม่รู้ว่าช่องพวกนั้นรับเลข 10–20 ได้หรือเปล่า)

**เบี้ยกุญแจ (unique key)** — เคสที่คุณยกว่า "ต้องใช้เลข 5 เท่านั้น":
สำหรับ site ที่ `tokenCount == 1` และ `bestScore ≥ θ`

```
keyBonus(k) = bestScore(site) × P(ฝ่ายตรงข้ามไม่มีเบี้ยนั้น) × horizon
P(...) = hypergeometric จาก unseen pool — เป็นตัวเลขจริง ไม่ใช่ bias
```

ถ้า site นั้นคือทางชนะเด็ดขาด (ชั้น endgame ในข้อ 5 เป็นคนบอก) ค่าจะอิ่มตัวที่
"เบี้ยตัวนี้คือทั้งเกม" ซึ่งเป็นพฤติกรรมที่ต้องการพอดี

### 2.3 กรณี `=` โดยเฉพาะ

วันนี้ `equalsSchedule` ถูกคูณด้วย `mobility` ([eval.cpp:90](../src/eval.cpp)) เปลี่ยนเป็น

```
equalsUrgency = (equalsGatedSites + newEquationCapacity)
              / max(1, equalsFreeSites + extendCapacity)
```

อ่านตรงตามที่คุณอธิบาย:

| สถานการณ์ | ตัวเศษ | ตัวส่วน | ผล |
|---|---|---|---|
| ทั้งกระดานไม่มี `=` เปิด และไม่มีที่ขยาย | สูง | ≈0 | `=` พุ่งสุด |
| ไม่มี `=` เปิด แต่ขยายสมการเดิมได้เยอะ | สูง | สูง | `=` ปกติ — ไม่ต้องใช้ก็ทำแต้มได้ |
| มีที่ขยายเยอะ แต่แต้มที่ทำได้น้อยเทียบกับกอง | สูง | ปานกลาง | `=` ขึ้น (ตามที่คุณบอกว่า "ค่าจะเพิ่มขึ้นไปอีก") |
| `=` เปิดหลายที่ | ต่ำ | สูง | `=` ถูกลง ควรใช้/แลกทิ้ง |

เพิ่มอีกชั้น: `=` มีในเกม 11 ตัว นับจากกระดาน + มือเราแล้วเหลือใน unseen เท่าไร
ถ้า unseen เหลือ `=` 1 ตัวและมี 6 ช่องที่ต้องใช้ `=` → **ทั้งความสามารถของคู่ต่อสู้
ในการเปิดสมการใหม่ก็ถูกจำกัดด้วย** ซึ่งเปลี่ยนทั้งค่ารุกและค่ารับพร้อมกัน

## 3. การจัดอันดับความสำคัญของพื้นที่

ให้ทุก site มีค่า `importance` เดียว รวม 5 แกน

| แกน | คำนวณจาก | ความหมาย |
|---|---|---|
| `points` | `bestScore` | แต้มที่ทำได้ตรงนั้น |
| `exclusivity` | `1/tokenCount` | มีเบี้ยกี่ชนิดที่ใช้ช่องนี้ได้ |
| `contest` | hypergeometric บน unseen | โอกาสที่คู่ต่อสู้มีเบี้ยที่ลงช่องนี้ได้ |
| `leverage` | premium ข้างเคียง + จำนวน site ที่จะเกิดตามมา | ลงแล้วเปิดหรือปิดกระดาน |
| `decisiveness` | ชั้น endgame (ข้อ 5) | ช่องนี้ตัดสินผลแพ้ชนะหรือไม่ |

ใช้สองทาง

**รุก** — ตาที่กินช่องซึ่ง "มีแต่เราใช้ได้" ทันที ได้ค่าเพิ่ม เพราะมันปิดประตูคู่ต่อสู้ไปด้วย

**รับ** — แทน `defensePenalty` ที่วันนี้นับแค่ "มีช่อง ×3 อยู่ข้าง ๆ ไหม"
([eval.cpp:118](../src/eval.cpp)) ด้วย

```
defense(move) = Σ importance ของ site ที่ตานี้ "สร้าง" ให้คู่ต่อสู้
              − Σ importance ของ site ที่ตานี้ "ทำลาย"
```

**ข้อควรระวังเรื่องต้นทุน (สำคัญ)** — `defensePenalty` ถูกเรียกทุกตาเดินใน loop
[engine.cpp:2624](../src/engine.cpp) ซึ่งมีเป็นพัน ๆ ตา จึงต้องทำ 2 ระดับ

1. **ระดับ admission (ทุกตาเดิน)** — precompute `siteValue[BOARD_CELLS]` ครั้งเดียวต่อตา
   แล้ว defense = Σ `siteValue[]` ของช่องที่ติดกับ placement
   *รูปร่างเดียวกับโค้ดวันนี้ ต้นทุนเท่าเดิม แต่ตัวเลขต่อช่องเป็นค่าโอกาสจริง
   แทนที่จะเป็นชนิด premium ดิบ* — นี่คือของฟรีที่ควรทำก่อนเพื่อน
2. **ระดับ candidate (60 ตัวที่ผ่านเข้า sim)** — คำนวณ SpaceMap delta จริงหลังลงเบี้ย
   (recompute cross เฉพาะช่องที่กระทบ ≈ 30 ช่อง × 26 validateLine)

## 4. โมเดลคู่ต่อสู้ได้ตาชุดเดียวกัน + ได้ sample คืน

`simulate()` เรียก `oppReplyValue` ซึ่ง **รัน movegen เต็ม ๆ ต่อ (sample × candidate)**
([engine.cpp:580](../src/engine.cpp)) นี่คือสาเหตุที่รายงานวินิจฉัยพบว่า sim อดอยาก sample

เมื่อมี SpaceMap ของกระดานหลังตาเรา จะได้ **ขอบเขตบนเชิงวิเคราะห์** ของตาตอบคู่ต่อสู้

```
oppUpperBound = max over sites, tokens ของ  score(site,token) · 1(oppRack มี token นั้น)
```

ใช้เป็น **branch-and-bound**: ถ้าขอบบนของ candidate นี้ยังแย่กว่าค่าจริงของผู้นำอยู่แล้ว
→ ข้าม movegen ไปเลย งบที่ประหยัดได้แปลงเป็นจำนวน sample ตรง ๆ
(ไม่ใช่การประมาณที่ทำให้อ่อนลง — เป็น bound ที่ไม่มีวันตัดตาที่ดีกว่าออก)

## 5. ปลายเกม: ตารางโอกาสของเบี้ยที่มองไม่เห็น

เมื่อ `unseen.total ≤ ~16` (ก่อนถึงเขตที่ `solveHiddenEndgame` พิสูจน์ได้)
แจกแจงแบบครบถ้วน: **ทุก site × ทุกชนิดเบี้ยที่ยังไม่เห็น → ลงได้ไหม เป็นสมการอะไร กี่แต้ม**

ได้ผลผลิต 2 อย่าง

**5.1 การกระจายภัยคุกคามที่แม่นยำ แทนการสุ่มมือ 160 ครั้ง**
P(คู่ต่อสู้ถือเบี้ยที่ลง site นี้ได้) เป็น hypergeometric แบบปิด — แม่นและถูกกว่าการสุ่ม
สำคัญเพราะ [ข้อ 4.8 ของรายงานวินิจฉัย](bot-strength-diagnosis.md) ชี้ว่า
บอทวางแผน **ทางเข้า** endgame ด้วย heuristic ที่พังทั้งหมด แล้วค่อยเริ่มพิสูจน์
ตอนที่ผูกมัดตัวเองไปแล้ว — ชั้นนี้คือการซ่อมช่วง 2–4 ตาก่อนกองหมด

**5.2 การบล็อก — ความสามารถที่เอนจินวันนี้ "พูดไม่ได้" เลย**
ระบุ site ที่คู่ต่อสู้ *ต้องใช้* เพื่อทำแต้ม/เพื่อลงหมดมือ แล้วให้ค่ากับตาที่ฆ่ามันทิ้ง
วันนี้ตาบล็อกมักได้แต้มต่ำ → `staticEquity` จัดอันดับไว้ท้ายแถว → ถูกตัดทิ้งที่ `simTopK = 60`
ก่อนที่ sim จะได้เห็นด้วยซ้ำ **จึงต้องเพิ่มโควตา candidate ประเภท "บล็อก" แยกต่างหาก**
ไม่งั้นต่อให้ประเมินค่าถูก ตานั้นก็ไม่เคยเข้ารอบ

## 6. ลำดับการทำ และเกณฑ์วัดของแต่ละเฟส

ทุกเฟสวัดด้วยของที่มีอยู่แล้ว: `amath_cli selfplay N tierA tierB seed`, `positions`, `golden`

| เฟส | สิ่งที่ทำ | เกณฑ์ผ่าน |
|---|---|---|
| **0** | เดินสาย SpaceMap เข้า `BoardContext` โดย **ไม่เปลี่ยนพฤติกรรม** + เขียน invariant test ข้อ 1.3 | `golden` ต้องเหมือนเดิมทุกบิต; SpaceMap < 1 ms |
| **1** | `equalsUrgency` + `heavyPlaceableSites` แทน `mobility` ใน `leaveValue` | selfplay ชนะ build เดิม |
| **2** | `tileValue[]` เต็มสูตร (access / supply / horizon / glut) | selfplay ชนะเฟส 1 |
| **3** | `siteValue[]` แทน premium ดิบใน `defensePenalty` (ระดับ 1) แล้วค่อยทำ delta (ระดับ 2) | selfplay + ไม่มี regression ที่ p95 latency |
| **4** | ขอบบนเชิงวิเคราะห์เป็น branch-and-bound ใน `oppReplyValue` | จำนวน sample ต่อตาเพิ่ม; ตาที่เลือกต้องไม่เปลี่ยนบน corpus (เป็น bound แท้) |
| **5** | ตารางโอกาส unseen + candidate class "บล็อก" | selfplay ช่วง bag ≤ 16 โดยเฉพาะ |

**ค่าคงที่ใหม่ทุกตัวต้องไปอยู่ใน `LeaveWeights`** เพื่อให้ `applyWeights`
([engine.cpp:132](../src/engine.cpp)) ตั้งค่าจาก request ได้ → tuner ที่มีอยู่กวาดค่าได้ทันที
อย่าฝังตัวเลขไว้ในโค้ดใหม่

## 7. คลาสของความผิดพลาดที่จะหายไป

ไม่ใช่คำสัญญาเรื่องเปอร์เซ็นต์ แต่คือรายการอาการที่วันนี้เอนจิน **ไม่มีทางเห็นได้เลย**
เพราะข้อมูลไปไม่ถึงฟังก์ชันค่า

1. แลก/ทิ้ง `=` ตัวสุดท้ายบนกระดานที่ไม่มีที่ขยายเหลือ
2. เก็บ 19 / 13 / 17 ไว้บนกระดานที่ไม่มีช่องไหนรับเลขสองหลักได้เลย
3. เปิด site ที่คู่ต่อสู้มีโอกาส 60% ถือกุญแจอยู่ (วันนี้เห็นแค่ว่า "ข้าง ๆ มี ×3 ไหม")
4. ขายเบี้ยกุญแจของตัวเองไปในราคาถูก ทั้งที่เป็นตัวเดียวที่เปิด site ใหญ่ได้
5. เข้า endgame ด้วยมือที่ผิด เพราะ 2–4 ตาก่อนหน้าใช้ heuristic ที่มองไม่เห็นกระดาน
6. ไม่เคยเลือกตาบล็อก เพราะมันไม่เคยผ่านด่าน `simTopK`

จุดอ้างอิงเชิงปริมาณที่มีอยู่: sim ที่ใช้จริงเลือกตาตรงกับ oracle **58.3%**
([deep-compute-allocation-report](deep-compute-allocation-report.md))
และ `leaveValue` คือฟังก์ชันที่ทั้ง endpoint ของ sim และการจัดอันดับ admission ใช้ร่วมกัน
— ปรับตรงนี้จึงยกทั้งสองด้านพร้อมกัน

## 9. ผลของเฟส 0 (31 ส.ค. 2026) — สองข้อที่เปลี่ยนแผนเฟส 1

เฟส 0 สร้าง `src/space_map.{hpp,cpp}` และพิสูจน์ทุกฟิลด์เทียบ `validatePlaceMove`
(ไม่ใช่เทียบ movegen — ดูเหตุผลข้างล่าง) ผ่านทั้งหมด และไม่เปลี่ยนพฤติกรรมเอนจิน
แต่การพิสูจน์ไปเจอสองอย่างที่ทำให้ต้องแก้แบบร่างข้างบน

### 9.1 movegen ทิ้งตาที่ถูกกฎ — ตาลง `=` เดี่ยว

`generatePlaceMoves` **ไม่เคยสร้างตาที่ลงเบี้ยตัวเดียวเป็นเครื่องหมาย (นอกจาก `-`)
เมื่อไม่มีเบี้ยติดอยู่ทางซ้ายของช่องนั้น**

สาเหตุ: ตาเบี้ยเดียวถูก emit จาก horizontal pass เท่านั้น
([movegen.cpp](../src/movegen.cpp) `emitIfValid`) และ `startAt` seed `LineState`
จาก prefix ทางซ้ายอย่างเดียว เมื่อไม่มี prefix เบี้ยที่ลงจึงถูกตัดสินในฐานะ
**token แรกของบรรทัดแนวนอน** แล้ว `LineState::advance` ปฏิเสธเครื่องหมายนำหน้า
ทั้งที่ช่องนั้นไม่มีเพื่อนบ้านแนวนอน → ไม่มี run แนวนอนอยู่จริง
(`validatePlaceMove` ข้ามด้วย `if (run.size() < 2) continue`)
เป็นการบังคับใช้กฎโครงสร้างกับบรรทัดที่ไม่มีอยู่

วัดบน 175 ตำแหน่ง: พลาดตาที่ถูกกฎ 14 ตา ใน 12 ตำแหน่ง โดย **5 ตาเป็นการลง `=` เดี่ยว**
และแต้มสูงสุดที่มองไม่เห็นคือ 20 แต้ม

ผลต่อแผนนี้โดยตรง: ค่าของ `=` ที่เอกสารนี้ทั้งฉบับพยายามจะประเมินให้ถูก
ส่วนหนึ่งมาจากตาที่เอนจิน**สร้างไม่ได้** การจูนค่า `=` ก่อนแก้ตัวสร้างตา
คือการจูนให้เข้ากับกระดานที่เอนจินมองเห็นผิด — ต้องแก้ movegen ก่อนเฟส 1

เฟส 0 ไม่แก้ (สัญญาว่าจะไม่เปลี่ยนพฤติกรรม) แต่ **quarantine** ไว้:
`tests/test_space_map.cpp` บังคับว่าทุกความไม่ตรงกันต้องเข้า predicate นี้เป๊ะ
และต้องถูกยืนยันว่าถูกกฎโดย `validatePlaceMove` — อย่างอื่นทดสอบตก

### 9.2 `heavyPlaceableSites` เป็นศูนย์เสมอ — พิสูจน์ได้ ไม่ใช่แค่ไม่เจอ

ข้อ 2.2 เสนอให้ใช้ "จำนวนช่องที่รับเลข 10–20 ได้" มาแทน `mobility`
ในเทอม `heavyBurden` ปรากฏว่าปริมาณนี้เป็น **0 เสมอ** สำหรับการลงเบี้ยตัวเดียว

พิสูจน์: token 10–20 ห้ามติดกับตัวเลข ดังนั้นเพื่อนบ้านทั้งสองข้างใน run
ต้องเป็นเครื่องหมายหรือไม่มี บนกระดานที่ถูกกฎ ชิ้นส่วนที่ติดกับช่องว่างคือ
maximal run ยาว ≥ 2 (ซึ่งเป็นสมการสมบูรณ์ จึงลงท้ายด้วยตัวเลข และขึ้นต้นด้วย
ตัวเลขหรือ `-` เอกภาค) หรือไม่ก็เบี้ยเดี่ยว ทุกกรณีที่เหลือบังคับให้ค่าที่ช่องเป็น 0:
การเติม X หน้าข้างที่ขึ้นต้นด้วย `-` เอกภาค เลื่อนค่าข้างนั้นไปพอดี X
สมดุลจึงต้องการ X = 0 ∎

แปลว่าเลขหนักเข้าเกมได้เฉพาะเป็นส่วนของ **ตาหลายเบี้ย** เท่านั้น
สัญญาณ "วางเลขหนักได้ไหม" ของเฟส 1 จึงต้องนิยามบนตาหลายเบี้ย ไม่ใช่บน mask ช่องเดียว

### 9.3 ผลพลอยได้: พื้นที่ขยายกับพื้นที่ไขว้ใช้กลไกเดียวกัน

ร่างเดิมแยก HookSite กับ ExtendSite เป็นคนละเรื่อง จริง ๆ แล้ว
**การขยาย 1 เบี้ย คือ mask ของอีกทิศทางหนึ่งพอดี** — `crossH[cell].mask` คือ
เซตของ token ที่ทำให้ run แนวนอนผ่านช่องนั้นเป็นสมการที่ถูก ซึ่งก็คือ
"ต่อสมการเดิมด้วยเบี้ยตัวเดียว" นั่นเอง `SpaceMap` จึงเก็บ `playMask = maskV & maskH`
เป็นความจริงเดียว และ `ExtendSite` เหลือเป็น **โทโพโลยีล้วน** (ที่ว่างข้างสมการ)
ซึ่งไม่อ้างว่าตาหลายเบี้ยใด ๆ ถูกกฎ — เฟส 0 หยุดตรงที่พิสูจน์ได้
