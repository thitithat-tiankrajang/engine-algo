ผมวัดด้วยการให้บอทเล่นกันเอง 3 ชุด รวม 18 เกม ผลออกมาชี้ขาด:

| การแข่ง | ผล | แต้มเฉลี่ยต่อเกม | เวลาคิดต่อตา |

| `hard` vs `easy` (seed 4242) | **0–6** | **−132.0** | 2,800 ms vs 81 ms |

`easy` คือการให้คะแนนแบบตายตัว ไม่มีการมองล่วงหน้าเลย

**ปัญหาไม่ใช่ "บอทคิดตื้นไป" แต่คือ "ส่วนที่คิดลึกกำลังคิดผิด"**

มันเชียร์ให้ตัวเองเปิดกระดาน แล้วมองไม่เห็นการลงโทษที่ตามมา

รายงานนี้อธิบายว่าบอทคิดยังไงทีละขั้น ให้น้ำหนักกับอะไรบ้าง แล้วชี้ว่าจุดไหนพัง

## 1. บอทคิดยังไง — เส้นทางการตัดสินใจทีละขั้น

ทุกครั้งที่ถึงตาบอท จะเกิดลำดับนี้เสมอ (`handleRequest`, [engine.cpp:1453](../src/engine.cpp))

```
รับโจทย์ JSON
   board, rack, bagCount, oppRackCount, myScore, oppScore, solver, budgetMs
        │
        ▼
[1] makeContext  — อ่าน "บริบท" ของกระดานออกมา 5 ตัวเลข
        │
        ▼
[2] generatePlaceMoves — สร้างตาเดินที่ถูกกฎ "ทั้งหมด"
        │           (มีเพดาน 32M โหนด สำหรับ static / 40 วินาที สำหรับ sim)
        ▼
[3] ถ้า bag ≤ 1 และเบี้ยเหลือทั้งหมด ≤ 13 → แก้ endgame แบบพิสูจน์ผลจริง  ──► ตอบ
        │
        ▼
[4] จัดอันดับทุกตาเดินด้วย staticEquity = คะแนน + คุณค่าเบี้ยที่เหลือ − ความเสี่ยงที่เปิดให้
        │
        ├── solver = "static"  (tier easy) ────────────────────────────────► ตอบตัวที่ 1
        │
        ▼
[5] solver = "sim" (medium / hard / max)
        เอา 60 อันดับแรก + ตัวเลือกแลกเบี้ยทุกขนาด + ตัวเลือก pass
        → simulate() : สุ่มมือคู่ต่อสู้มาหลาย ๆ แบบ แล้วเทียบทุกตัวเลือกบนมือชุดเดียวกัน
        │
        ▼
[6] จัดอันดับใหม่ด้วย  mean − λ·stddev  แล้วตอบตัวที่ดีที่สุด
```

จุดที่ต้องเน้น 3 อย่าง

1. **`easy` กับ `medium/hard/max` ใช้ตัวคัดกรองตัวเดียวกันในขั้น [4]** ต่างกันแค่
   `easy` หยุดตรงนั้นเลย ส่วนที่เหลือเอา 60 อันดับแรกไปจำลองต่อ
2. **ขั้น [3] เกิดก่อนการเลือก solver เสมอ** ดังนั้นแม้ `easy` ก็ยังได้ endgame ที่พิสูจน์แล้ว
3. **WASM ในเบราว์เซอร์กับ service บนเซิร์ฟเวอร์เรียก `handleRequest` ตัวเดียวกัน**
   ([`src/wasm_api.cpp`](../src/wasm_api.cpp)) ทุกอย่างในรายงานนี้จึงใช้กับทั้งสองทาง

## 2. บอทให้น้ำหนักกับอะไร

### 2.1 บริบทกระดาน 5 ตัว (`BoardContext`)

| ตัวแปร | ความหมาย | **ถูกใช้จริงไหม** |
|---|---|---|
| `mobility` | กระดานเปิดแค่ไหน (นับช่องว่างที่ติดกับเบี้ยเดิม หาร 40) | ✅ ใช้ |
| `freshTileValue` | เบี้ยที่จับใหม่จากกองน่าจะมีค่าเท่าไร | ⚠️ ใช้เฉพาะตอนคิดค่าการ "แลกเบี้ย" |
| `scoreDiff` | ฉันนำ/ตามอยู่กี่แต้ม | ⚠️ ใช้แค่ 2 ที่ (โบนัสแลกเบี้ย, ค่า λ) |
| `bagSize` | เหลือเบี้ยในกองกี่ตัว | ❌ **ไม่เคยถูกอ่านเลย** |
| `unseenTotal` | เบี้ยที่ยังไม่เห็นทั้งหมด | ❌ **ไม่เคยถูกอ่านเลย** |

นี่คือปัญหาข้อแรกที่มองเห็นได้จากโค้ดตรง ๆ: **โมเดลประเมินมือเบี้ยของบอทไม่รู้ว่าตอนนี้เกมอยู่เฟสไหน**
มันตีค่ามือเบี้ยชุดเดียวกันเท่ากันเป๊ะ ไม่ว่าจะเป็นตาแรกของเกม (กองเหลือ 80 ตัว)
หรือช่วงกองใกล้หมด (เหลือ 3 ตัว) ทั้งที่ในเกมประเภทนี้ การจัดการมือเบี้ยช่วงท้ายกอง
คือจุดที่แต้มต่างกันมากที่สุด

### 2.2 คะแนนแบบตายตัว: `staticEquity`

```
staticEquity(ตาเดิน) = คะแนนที่ได้ทันที
                     + leaveValue(เบี้ยที่เหลือในมือ)
                     − defensePenalty(ช่องพิเศษที่เปิดให้คู่ต่อสู้)
```

**`defensePenalty`** — คิดจากช่องว่างที่ติดกับเบี้ยที่เราเพิ่งวาง

| ช่อง | ค่าปรับ |
|---|---|
| ×3 สมการ (EX3) | −4.0 |
| ×2 สมการ (EX2) | −2.0 |
| ×3 เบี้ย (PX3) | −1.2 |

**`leaveValue`** — คุณค่าของเบี้ยที่ค้างในมือหลังเดิน ประกอบด้วย

| องค์ประกอบ | น้ำหนัก | เหตุผลที่ตั้งไว้ |
|---|---|---|
| ค่าพื้นฐานรายเบี้ย | ดูตาราง `kindValue` ด้านล่าง | |
| `?` (blank) | **+10.0** | ยืดหยุ่นที่สุดในเกม |
| `+/−` และ `×/÷` (choice) | +3.2 / +2.3 | เล่นได้สองหน้า |
| 19 / 13 / 17 | +3.0 / +2.8 / +2.8 | เลขหนักที่ทำแต้มได้เยอะ |
| 10 / 11 / 12 | −0.5 / −0.2 / −0.3 | หนักแต่ทำแต้มไม่คุ้ม |
| `=` ตัวที่ 1 / 2 / 3 / 4 | +3.0 / +0.5 / −3.0 / −7.0 | ตัวแรกเกือบจำเป็น ตัวที่สามเริ่มตัน |
| 0 คู่กับ × หรือ ÷ | +1.2 ต่อคู่ | 0 เข้ากับคูณหารได้ดี |
| 0 แต่ไม่มี × ÷ เลย | −1.2 ต่อตัว | 0 กับบวกลบใช้ยาก |
| เลขหนัก (10–20) เกิน 1 ตัว | −3.0 × (เกิน)² | ยิ่งกองยิ่งตัน (เบาลงถ้ากระดานเปิด) |
| ตัวดำเนินการไม่พอ | −7.0 ต่อตัวที่ขาด | ต้องมีราว 0.45 ตัวดำเนินการต่อ 1 เลข |
| ไม่มีตัวดำเนินการเลย (และมีเลข ≥2) | −10.0 | มือเกือบตาย |
| เลขหนักมากกว่าตัวประกบ | −6.0 ต่อตัว | เลขหนักติดเลขอื่นไม่ได้ ต้องมีตัวคั่น |
| เบี้ยซ้ำกัน | −1.0 ต่อตัวซ้ำ | |
| สัดส่วนตัวเลขเบี่ยงจาก 60% | −1.2 ต่อตัวที่เบี่ยง | |

โมเดลนี้เขียนได้ดีและมีความรู้เกม A-Math จริงอยู่ในนั้น **ปัญหาไม่ได้อยู่ตรงนี้**

### 2.3 ค่าที่ใช้ตัดสินในโหมดจำลอง (`sim`)

สำหรับแต่ละมือคู่ต่อสู้ที่สุ่มมา 1 ชุด บอทคิดแบบนี้

```
ค่าของตาเดินนี้ = คะแนนที่ได้ทันที
                + leaveValue(มือหลังเติมเบี้ยจากกอง)
                + 0.60 × (คะแนนสูงสุดที่มือใหม่จะทำได้ในตาหน้า)   ← "potential"
                − (ค่าตาที่ดีที่สุดของคู่ต่อสู้)                      ← "oppReply"
```

แล้วจัดอันดับด้วย

```
คะแนนสุดท้าย = ค่าเฉลี่ยข้าม sample  −  λ × ส่วนเบี่ยงเบนมาตรฐาน
λ = 0.18 + 0.22 × (แต้มที่นำอยู่ / 50)
```

### 2.4 ตัวอย่างจริง — บอทคิดเลขออกมาหน้าตาแบบนี้

ตำแหน่งกลางเกมจริง ผ่าน tier `hard` (budget 4,000 ms):

| ตัวเลือก | คะแนน | leave | potential | oppReply | mean | stddev | **ค่าที่ใช้ตัดสิน** |
|---|---:|---:|---:|---:|---:|---:|---:|
| **ที่เลือก** | 78 | 12.61 | **68.80** | **147.79** | 5.38 | 37.66 | **−4.72** |
| อันดับ 3 | 72 | 6.36 | 40.20 | 114.25 | 4.31 | 40.29 | −6.49 |
| อันดับ 10 | 74 | 6.36 | 34.60 | 113.59 | 1.38 | 37.66 | −8.72 |
| อันดับ 12 | 76 | 12.61 | 66.60 | 139.72 | 0.51 | 35.04 | −8.88 |

อ่านตารางนี้แล้วเห็นปัญหาทันที 3 อย่าง

1. **`potential` (68.80) ใหญ่เกือบเท่าคะแนนจริง (78)** — โบนัส "ตาหน้าฉันจะทำได้เยอะ"
   มีน้ำหนักเกือบเท่าแต้มที่ได้จริง ๆ ทั้งที่คู่ต่อสู้จะเดินคั่นก่อน
2. **`oppReply` (147.79) ใหญ่กว่าทุกอย่างรวมกัน** — ค่าทั้งหมดถูกกำหนดโดยตัวเลขที่
   บอทประเมินคู่ต่อสู้ ซึ่ง (จะพิสูจน์ในข้อ 4.3) เป็นตัวเลขที่ผิดบ่อยมาก
3. **`stddev` (37.66) ใหญ่กว่าช่องว่างระหว่างตัวเลือก (~1–4) ถึงสิบเท่า** —
   สัญญาณจมอยู่ใต้สัญญาณรบกวน

## 3. Scale เป็นยังไง — วัดจริงต่อ tier

ผมยิงตำแหน่งกลางเกมเดียวกันเข้าไปทุก budget แล้ววัดว่าได้ sample กี่ชุดจริง ๆ

| tier | budget ที่ตั้งไว้ | **sample ที่ได้จริง** | **เวลาที่ใช้จริง** | genCalls | ตาที่เลือก |
|---|---:|---:|---:|---:|---:|
| `medium` | 1,000 ms | **3** | 3,284 ms | 386 | คะแนน 78 |
| `hard` | 4,000 ms | **3** | 3,615 ms | 415 | คะแนน 78 |
| (ทดสอบ) | 20,000 ms | 16 | 18,006 ms | 2,105 | คะแนน 78 |
| `max` | ไม่จำกัด (เพดาน 120 s) | 99 | **108,001 ms** | 12,591 | คะแนน 78 |

### สิ่งที่ตารางนี้บอก

**`medium` กับ `hard` คือบอทตัวเดียวกัน** — ได้ 3 sample เท่ากัน ใช้เวลาเท่ากัน
ตอบเหมือนกัน ผู้เล่นที่เลือก "ยาก" ได้บอทตัวเดียวกับ "ปานกลาง" เป๊ะ

สาเหตุอยู่ใน `simulate()` ([engine.cpp:435](../src/engine.cpp) และ 527):
เงื่อนไขหยุดคือ `elapsed > budgetMs && done >= 3` — **ต้องจบ 3 sample ให้ครบก่อนเสมอ**
ไม่ว่า budget จะเป็นเท่าไร และ 3 sample บนกระดานกลางเกมใช้เวลาราว 3.3 วินาที
ดังนั้น budget ทุกค่าที่ต่ำกว่า ~3.3 วินาที ให้ผลเหมือนกันหมด
(ไฟล์ `levels.ts` เขียนคำเตือนเรื่องนี้ไว้แล้ว แต่ค่า tier ยังไม่ถูกแก้)

**`max` แพงกว่า 30 เท่าเพื่อคำตอบเดิม** — 108 วินาทีต่อหนึ่งตาเดิน
ได้ 99 sample แล้วเลือกตาเดิม ในตำแหน่งนี้

## 4. ทำไมยังไม่เก่ง — สาเหตุเรียงตามผลกระทบ

### 4.1 การจำลองอดอยาก sample อย่างรุนแรง (3 ชุด)

บอทกำลังเลือกระหว่างตัวเลือกที่ค่าต่างกัน **1–4 แต้ม** โดยใช้เครื่องมือวัดที่มี
ส่วนเบี่ยงเบนมาตรฐาน **37–77 แต้ม** จาก **3 จุดข้อมูล**

การใช้ common random numbers (ทุกตัวเลือกเจอมือคู่ต่อสู้ชุดเดียวกัน) ช่วยลดสัญญาณรบกวน
ส่วนที่ร่วมกันได้จริง แต่ 3 ชุดก็ยังน้อยเกินกว่าจะแยกตัวเลือกที่ห่างกัน 1 แต้มได้

### 4.2 งบจำลองกว่าครึ่งหมดไปกับตัวเลือกที่ซ้ำกัน

บอทเอา 60 ตาเดินแรกเข้าไปจำลอง ผมนับว่าใน 60 ตัวนั้น มีกี่ตัวที่ให้ผลประเมิน
**ต่างกันจริง**

| ตำแหน่ง | ตาเดินที่จำลอง | ผลประเมินที่ต่างกันจริง | **งบที่เสียไปกับตัวซ้ำ** | sample ที่ได้ |
|---|---:|---:|---:|---:|
| pos 0 | 60 | 15 | **75.0%** | 3 |
| pos 1 | 60 | **3** | **95.0%** | 4 |
| pos 2 | 60 | 35 | 41.7% | 3 |
| pos 3 | 60 | 48 | 20.0% | 3 |

ในตำแหน่งที่ 1 บอทใช้แรงประเมิน 60 ตาเดิน เพื่อได้ข้อมูลที่ต่างกันจริงแค่ 3 ชุด
นี่คือสาเหตุโดยตรงของ 4.1 — ถ้ายุบตัวซ้ำก่อนจำลอง ตำแหน่งนั้นจะได้ sample
มากขึ้นราว 20 เท่าด้วยงบเท่าเดิม

`GenOptions::dedup` ยุบเฉพาะ "การตีความ blank แบบต่าง ๆ ของการวางชุดเดียวกัน"
แต่ตาเดินที่ต่างกันทางกายภาพและบังเอิญให้ค่าเท่ากันเป๊ะ (เช่นวางกระจกซ้าย/ขวา)
ยังถูกจำลองแยกกันทุกตัว

### 4.3 โมเดลคู่ต่อสู้ถูกตัดกลางคัน — และผิดมาก

`oppReplyValue` จำกัดการค้นหาตาตอบของคู่ต่อสู้ไว้ที่ **200,000 โหนด**
([engine.cpp:393](../src/engine.cpp)) ส่วน `bestPlaceScore` จำกัดที่ **150,000 โหนด**
เทียบกับ root generation ของตัวเองที่ได้ **32,000,000 โหนด** — ต่างกัน 160 เท่า

ผมวัดบนตำแหน่งจริง 209 ตำแหน่งจาก 10 เกม:

```
โหนดที่ต้องใช้เพื่อค้นหาตาตอบของคู่ต่อสู้ให้ครบ:
   p50 83,505 | p90 1,840,927 | p95 4,861,263 | p99 14,990,831 | max 17,456,708

-- เพดาน 200k (โมเดลคู่ต่อสู้ของบอท) --
ถูกตัดกลางคัน:               70/209  (33.5%)
มองไม่เห็นตาที่ดีที่สุดของคู่ต่อสู้:  31/209 (14.8%)  พลาดเฉลี่ย 37.0 แต้ม  แย่สุด 100 แต้ม
มองไม่เห็น equity ที่ดีที่สุด:     35/209 (16.7%)  พลาดเฉลี่ย 33.0      แย่สุด 100.8

-- เพดาน 150k (โมเดล "ตาหน้าของฉันเอง") --
ถูกตัดกลางคัน:               84/209  (40.2%)
มองไม่เห็นตาที่ดีที่สุด:          36/209 (17.2%)  พลาดเฉลี่ย 41.2 แต้ม  แย่สุด 108 แต้ม
```

**หนึ่งในหกครั้ง บอทประเมินคู่ต่อสู้ต่ำไปโดยเฉลี่ย 37 แต้ม**

และตำแหน่งที่ถูกตัดคือตำแหน่งที่กระดานเปิดและมีตาเดินเยอะ — คือตำแหน่งที่การป้องกัน
สำคัญที่สุดพอดี บอทจึงมองโลกในแง่ดีเกินจริงในจังหวะที่มันควรระวังที่สุด

### 4.4 ฟังก์ชันค่าไม่สมมาตร — บอทให้โบนัสตัวเองแต่ไม่ให้คู่ต่อสู้

```
ค่าของฉัน       = คะแนน + leave + 0.60 × (คะแนนตาหน้าของฉัน)     ← มีโบนัสอนาคต
ค่าของคู่ต่อสู้  = คะแนน + leave − ค่าปรับป้องกัน                   ← ไม่มีโบนัสอนาคต
```

บอทคิดว่า "ฉันจะได้ทำแต้มอีก 68.8 ในตาหน้า" แต่ไม่คิดว่าคู่ต่อสู้ก็ได้เหมือนกัน
ผลคือ **บอทประเมินตาเดินของตัวเองสูงเกินจริงอย่างเป็นระบบ**

แย่กว่านั้น: `bestPlaceScore` คำนวณบนกระดาน **หลังจากที่ฉันวางแล้ว แต่ก่อนที่คู่ต่อสู้จะเดิน**
แปลว่าถ้าฉันเปิดช่องทำแต้มใหญ่ไว้ บอทนับช่องนั้นเป็นกำไรของตัวเอง
ทั้งที่คู่ต่อสู้ได้เดินก่อนและมักจะยึดช่องนั้นไปเลย

เอกสารออกแบบ Revision 2 ของทีมเองก็สรุปแบบนี้
([aether-search-v2-design.md](aether-search-v2-design.md) §1):
เทอมนี้ *"ไม่ใช่ ply ที่สามจริง ๆ"*, memo แทบไม่เคยถูกใช้ซ้ำ, และการทดลองแทนที่ด้วย
ของถูก ๆ ให้ผล *แยกไม่ออกจากการตัดเทอมนี้ทิ้งไปเลย* — แต่มันกิน **45.3% ของเวลาคิดทั้งหมด**

### 4.5 โหมด sim ทิ้ง heuristic ป้องกันที่โหมด static มี

| | คิดค่าปรับป้องกันไหม |
|---|---|
| `staticEquity` (ใช้ใน `easy` และตอนคัดกรอง) | ✅ ลบ `defensePenalty` ออกตรง ๆ |
| ค่าของตาเดินตัวเองใน `simulate()` | ❌ **ไม่มี** — [engine.cpp:473](../src/engine.cpp) |

โหมด sim ตั้งใจถอด heuristic ป้องกันออก แล้วไปพึ่งการจำลองคู่ต่อสู้แทน
ซึ่งเป็นการแลกที่ถูกต้องในทางทฤษฎี — **ถ้า** การจำลองแม่น
แต่จากข้อ 4.1–4.3 การจำลองได้ 3 sample และผิด 1 ใน 6 ครั้ง

**นี่คือกลไกหลักที่ทำให้ `hard` แพ้ `easy`**: `easy` โดนหักคะแนนทุกครั้งที่เปิดช่อง ×3
ส่วน `hard` ถอดตัวหักนั้นออก แล้วเอาไปแลกกับกล้องส่องคู่ต่อสู้ที่พร่ามัว
พอรวมกับข้อ 4.4 ที่ให้โบนัสกับการเปิดกระดาน ผลคือ **บอทถูกผลักให้เปิดกระดานสองทาง
พร้อมกัน แล้วมองไม่เห็นราคาที่ต้องจ่าย**

#### พิสูจน์: ถาม solver ทั้งสองบนตำแหน่งเดียวกัน 93 ตำแหน่ง

|  | คะแนนเฉลี่ยของตาที่เลือก | ช่องพิเศษที่เปิดให้เฉลี่ย | ช่องใหม่ที่เปิด | pass/exchange |
|---|---:|---:|---:|---:|
| `sim` (hard) | **44.8** | **2.09** | 4.54 | 15 |
| `static` (easy) | **46.9** | **1.83** | 4.53 | 16 |

สองตัวเลือกตรงกัน 64.5% ของตำแหน่ง **เวลาที่ต่างกัน `sim` แย่กว่าทั้งสองด้าน**
คือได้แต้มน้อยกว่า และเปิดช่องพิเศษให้คู่ต่อสู้มากกว่า 14%

ตัวเลขนี้อธิบายผลแพ้ทั้งหมดได้พอดี: เสียแต้มเฉลี่ย 2.1 แต้มต่อตา บนราว 50 ตาวางต่อเกม
= **ราว 105 แต้มต่อเกม** ซึ่งตรงกับ margin ที่วัดได้จริง (−85 ถึง −132)

### 4.6 ตัวลงโทษความเสี่ยงคำนวณจากสัญญาณรบกวน

```
คะแนนสุดท้าย = mean − λ × stddev
λ = 0.18 + 0.22 × (แต้มที่นำ / 50)
```

ปัญหาสองชั้น

1. **`stddev` ประมาณจาก 3 จุด** ค่าที่ได้เองก็เหวี่ยงราว ±50%
   ตัวลงโทษจึงเป็นการสุ่มที่ถูกคูณด้วย λ
2. **ใช้ `stddev` แบบไม่จับคู่** ทั้งที่การจำลองใช้ common random numbers อยู่แล้ว
   ความผันผวนส่วนใหญ่ใน `stddev` มาจาก "มือคู่ต่อสู้ชุดนี้ดีหรือแย่" ซึ่งเป็นของ
   ที่ทุกตัวเลือกเจอเหมือนกัน ไม่ใช่ความเสี่ยงของตาเดินนั้น
   ตัววัดที่ถูกต้องคือส่วนเบี่ยงเบนของ **ผลต่าง** ระหว่างตัวเลือก ไม่ใช่ของตัวเลือกเดี่ยว

และเมื่อบอทนำอยู่ 130 แต้ม (ซึ่งเกิดบ่อย) λ = 0.75 คูณกับ stddev ~70
= ตัวลงโทษขนาด 52 แต้มที่คำนวณมาจากข้อมูล 3 จุด

### 4.7 โมเดลมือเบี้ยตาบอดต่อเฟสของเกม

จากตารางในข้อ 2.1: `leaveValue` อ่านแค่ `mobility` ตัวเดียว
`bagSize` และ `unseenTotal` ไม่เคยถูกอ่านเลยทั้งโปรเจกต์

ผลที่ตามมาในเกมจริง
- บอทเก็บ `?` (blank, +10.0) ไว้เหมือนกันหมด แม้กองใกล้หมดและควรรีบใช้
- บอทกลัวเก็บเลขหนัก (−3.0 × เกิน²) เท่ากันหมด แม้ตอนที่เหลืออีกไม่กี่ตาแล้ว
- ไม่มีแนวคิด "เร่งจบเกมเพื่อรักษาแต้มนำ" หรือ "ยื้อเกมเพราะกำลังตาม"
  (`scoreDiff` ถูกใช้แค่ในโบนัสแลกเบี้ยเล็ก ๆ ±0.6/0.4 กับค่า λ)

น้ำหนัก `exchangeConsiderBar = 6.0` ที่เขียนคอมเมนต์ไว้ว่าใช้คุมนโยบายแลกเบี้ย
**ไม่เคยถูกอ่านในโค้ดเลย** — เป็นสัญญาณว่าตารางค่าปรับจูนกับโค้ดจริงเริ่มไม่ตรงกัน

### 4.8 ตัวแก้ endgame แบบพิสูจน์ผล มาไม่ทันจังหวะสำคัญ

เงื่อนไขเข้าคือ `bag ≤ 1` **และ** `เบี้ยเหลือทั้งหมด ≤ 13`
วัดจริงบน 226 การตัดสินใจ: **27.0%** ได้ตัวแก้แบบพิสูจน์ผล ซึ่งถือว่าเยอะ

แต่ปัญหาคือ **ตาที่พลาดไปคือตาที่สำคัญที่สุด** — จังหวะแรกที่กองหมด
ตอนนั้นทั้งสองฝ่ายมักมีเบี้ยเต็มมือ รวมได้ 16–17 ตัว ซึ่งเกินเพดาน 13

```
skipped exact endgame: bag=0 tilesLeft=16 (cap 13)
skipped exact endgame: bag=1 tilesLeft=17 (cap 13)
skipped exact endgame: bag=0 tilesLeft=15 (cap 13)
...  (10 ครั้งจาก 226)
```

บอทจึงวางแผน **ทางเข้า** endgame ด้วย heuristic ที่มีปัญหาทั้งหมดข้างบน
แล้วค่อยเริ่มพิสูจน์เมื่อผูกมัดตัวเองไปแล้ว

### 4.9 สถาปัตยกรรมที่แก้ปัญหาเหล่านี้ ยังไม่ถูกต่อเข้าโปรดักชัน

`DecisionSearch` (Revision 2) มีอยู่ในโค้ดแล้วและแก้หลายข้อข้างบนตรง ๆ
แต่เข้าถึงได้เฉพาะผ่าน `DecisionSearch::benchmark` — **ไม่มีเส้นทางโปรดักชันเรียกถึง**

จากรายงานของทีมเอง ([deep-compute-allocation-report.md](deep-compute-allocation-report.md) §4.3)
เทียบกับ oracle อ้างอิงบน 24 ตำแหน่ง:

| | sim ที่ใช้อยู่จริง | ReplyIndexAdaptiveUniform |
|---|---:|---:|
| **เลือกตาตรงกับ oracle** | **58.3%** | **87.5%** |
| DFS nodes | 158.1M | 34.3M |
| p95 latency | 47,159 ms | 10,245 ms |
| regret เฉลี่ย | 2.002 | 0.425 |

**บอทที่ผู้เล่นเจออยู่ตอนนี้เลือกตาต่างจาก oracle 41.7% ของเวลา**
ในขณะที่ของที่ทำเสร็จแล้วในโค้ดทำได้ 87.5% ด้วยงานน้อยกว่า 4.6 เท่า

เหตุผลที่ยังไม่ปล่อยคือ gate G6/G7 ยังไม่ผ่าน (admission recall 95.8% จากที่ต้องการ 99%)
ซึ่งเป็นวินัยที่ดี — แต่ระหว่างนี้ผู้เล่นก็ยังได้ของเก่าที่วัดแล้วว่าแย่กว่าทุกแกน

### 4.10 (เล็ก) รายงาน "ทำไมถึงเดินตานี้" คำนวณผิด

ใน `simulate()` ตัวเลข `sumLeave` / `sumPot` / `sumOpp` ถูกบวกเข้าไป
**ในลูปตัวเลือก** ([engine.cpp:503–507](../src/engine.cpp)) แต่ `seen[i]` เพิ่มเฉพาะเมื่อ
sample นั้นจบครบทุกตัวเลือก ([engine.cpp:510–514](../src/engine.cpp))

แถวสุดท้ายที่ถูกตัดกลางคันจึงถูกนับใน sum แต่ไม่ถูกนับใน `seen`
ผลคือค่าที่โชว์ไม่บวกกลับเป็น `mean` — จากตัวอย่างข้อ 2.4:

```
78 + 12.61 + 68.80 − 147.79 = 11.62   แต่รายงานบอก mean = 5.38
```

ไม่กระทบตาที่เลือก แต่กระทบฟีเจอร์วิเคราะห์ที่ผู้เล่นเห็น

## 5. ควรทำอะไรต่อ — เรียงตามผลที่ได้ต่อแรงที่ลง

### ทำได้ทันที (ชั่วโมง ไม่ใช่สัปดาห์)

**1. เลิกใช้ `sim` สำหรับ tier ที่ต่ำกว่า `max` จนกว่าจะแก้เสร็จ**
วัดแล้วบน 18 เกมว่า `static` แข็งกว่า (ชนะ 16–2) และเร็วกว่าราว 30 เท่า เปลี่ยน `medium`/`hard` ใน
[`service/src/levels.ts`](../service/src/levels.ts) ให้เป็น `solver: "static"`
จะได้บอทที่แข็งขึ้นทันทีและตอบเร็วขึ้นมาก
(ถ้าต้องการให้ tier ต่างกันจริง ให้ต่างที่ `rootNodeLimit` แทน — ยังคง deterministic)

**2. ยุบตัวเลือกที่ให้ผลเหมือนกันก่อนเข้าจำลอง**
คืนงบ 20–95% ให้กับจำนวน sample ทันที โดยไม่ต้องแก้ตรรกะอะไรเลย

**3. แก้บั๊กรายงานในข้อ 4.10** ย้ายการบวก `sumLeave/sumPot/sumOpp` ไปไว้ใน
บล็อกเดียวกับ `accum`/`seen`

**4. แก้เรื่อง tier ที่ซ้ำกัน** ตั้ง budget ที่ต่ำกว่าเวลาที่ 3 sample ใช้จริง
ให้เป็น `static` ไปเลย — ไม่งั้นตัวเลข budget เป็นแค่การหลอกตัวเอง

### ต้องคิดหน่อย (วัน)

**5. ทำฟังก์ชันค่าให้สมมาตร** ถ้าจะเก็บเทอม `potential` ต้องให้คู่ต่อสู้ด้วย
หรือ (ที่เอกสาร Revision 2 แนะนำ) **ตัดทิ้งไปเลย** — จะได้เวลาคืนมา 45%
เอาไปเพิ่ม sample ได้เกือบสองเท่าทันที

**6. เอา `defensePenalty` กลับเข้ามาในเส้นทาง sim** อย่างน้อยจนกว่าโมเดลคู่ต่อสู้จะเชื่อถือได้
มันคือความแตกต่างเดียวที่อธิบายว่าทำไม `easy` ถึงชนะ

**7. เปลี่ยนตัวลงโทษความเสี่ยงให้ใช้ paired difference** และอย่าใช้เลยถ้า sample < 10

**8. ให้ `leaveValue` อ่าน `bagSize`** อย่างน้อยแบ่งเป็น 3 เฟส (เปิด / กลาง / กองใกล้หมด)
แล้วปรับค่า blank, เลขหนัก, และ `=` ตามเฟส

### ของใหญ่ (สัปดาห์)

**9. ปลด G6 แล้วเอา `ReplyIndexAdaptiveUniform` ขึ้นโปรดักชัน**
วัดแล้วว่าดีกว่าทุกแกน (87.5% vs 58.3%, งานน้อยกว่า 4.6 เท่า, p95 เร็วกว่า 4.6 เท่า)
ตามคำแนะนำในรายงานเดิมคือต้องขยาย oracle เป็น cap 96 ก่อน แล้วปรับ
plausibility envelope 90 แต้มที่ยังไม่เคยถูก fit กับข้อมูล held-out

**10. ขยายเพดาน `endgameExactTilesMax`** จาก 13 เป็น 16–17 (พร้อมวัดเวลา)
เพื่อให้ตาแรกหลังกองหมดได้การพิสูจน์จริง

**11. ปรับจูนน้ำหนักด้วยข้อมูล** ตอนนี้ทุกค่าใน `LeaveWeights` ตั้งด้วยมือทั้งหมด
(คอมเมนต์ในไฟล์ก็เขียนไว้เองว่าเป็น "BIAS POINTS" ที่รอ M5 tuner)
เมื่อ 1–8 เสร็จแล้วจะมี baseline ที่นิ่งพอให้จูนได้จริง
